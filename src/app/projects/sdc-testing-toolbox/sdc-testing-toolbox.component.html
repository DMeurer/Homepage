SDC Testing Toolbox

The SDC Testing Toolbox is a desktop app for playing around with IEEE 11073 SDC, the standard that lets medical devices talk to each other. You build a device by clicking, publish it on the network, and then control it from a second instance of the app. Or from any other SDC device.
If you have no idea what SDC is, my article SDC — What is this? might be a good starting point. This page assumes you roughly know.

I built it because reading the standard did not get me very far. SDC has a lot of concepts that only make sense once when you understand the basics. But I cant read all of the standards at once, so I built myself a small tool to make myself understand.

To be very clear: this is a learning and testing tool, not a medical device. Nothing about it is meant for clinical use.
And a small additional note: I am actively changing this thing over and over to fit my needs. Screenshots will very likely be out of date.

Start it twice

Every instance is two things at once. The My device side is the device you publish, the Network side is everything else. So the quickest demo is to start it twice and let the two find each other.

Both sides are live. Move a slider on the publisher and it moves in the subscriber a moment later. Move it in the subscriber and the provider gets a request to change it, which it can accept or refuse.

My device

This is where you build the device. New data source… creates a value: a number, a text, a choice from a fixed list, a waveform or a distribution. Those are pretty much the only value types SDC knows, which sounds limiting but means every other device knows how to show them. Numbers can get a range and a unit, and numbers, texts and choices can be marked as remote controllable.

Every value gets a card with the control that fits it: a slider when it has a minimum and a maximum, a dropdown for a choice, a plot for waveforms. Waveforms are generated on the fly, because a waveform with nothing behind it just looks broken. If you prefer tables, F9 switches every card into a table row.

Starting from nothing every time gets old fast, so there are presets. Nine devices you would find in an operating room ship with the app: a patient monitor, an insufflator, an HF generator, an infusion pump, a ventilator, an operating table and some more. Each one is a normal SDC device description (an MDIB file) with a few extra notes for the toolbox, so you can also load the MDIB of a real device and tinker with it. File → Export config saves your own device the same way.

Network

The other half. Scan finds every SDC device on the network, Connect loads one. Each connection gets its own tab, so you can watch several devices at once. The values show up as the same cards, and the ones the device lets you change are editable.

The interesting part is what happens when the device says no. Send a target pressure of 500 when only 0 to 30 is allowed, and the insufflator refuses it and tells you why. Switch off remote control on the device side, and the same write gets refused even though the value would be fine. The toolbox does not decide this for the other device, it just shows what the device answered.

The Network side does not assume the other end is another toolbox either. It works with any SDC device, shows parts it does not understand instead of dropping them, and copes with devices that leave out units or descriptions. So it doubles as a plain SDC browser for somebody else's implementation.

Alarms

Alarms are where SDC gets a little philosophical. An alarm is split into the condition ("the pressure is too high") and the signals that announce it (a light, a sound, a vibration). In the screenshot above the overpressure alarm is active, and you can see both of its signals, visual and audible, light up in the Signals column.

Give an alarm limits and it watches its value by itself. Push the value past the limit, from either side, and the alarm goes off on both. Acknowledge silences the signals but leaves the condition active, because the pressure is still too high. That is exactly the difference the split is there for.

Actions

Not everything a device does is a value. Reset the gas counter, vent to atmosphere, home the axes: there is nothing to type, you just press a button. These show up as a row of buttons at the bottom, on both sides. In the toolbox an action sets a few values, so you can actually see that it did something. Press Vent to atmosphere from the monitor and watch flow, pressure and mode on the insufflator change at once.

Looking under the hood

For the curious there is the MDIB structure section, the device's full description as a tree with all its handles, the IDs SDC uses for everything. Together with the table view it is the fastest way to see what a device really publishes.

And when you want to know what just happened, the Activity log in the status bar lists everything: values a connected device changed, actions it ran, alarms that went off.

One thing worth knowing: SDC discovery binds to a single network address, and a normal laptop has eight or nine of them (VPN, Hyper-V, Bluetooth, ...). If two instances on different machines cannot see each other, the address is the first thing to check. The start dialog lists them with the adapter name for exactly that reason.

By default everything runs over plain HTTP, so keep it on a network you trust. TLS with certificates is there if you need it.
